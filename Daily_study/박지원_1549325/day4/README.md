# 학습 일지 — React Native 로딩 성능 & UX 고도화

- **작성일**: 2026.07.16 (목)
- **주제**: 핀플(Pinple) 프로젝트 — 화면/브라우저 로딩에 영향을 주는 요인, UX 고도화 작업, 실제 현업 측정 사례
- **목표**: 로딩 속도 개선 포인트 파악 + 체감 UX 개선 작업 정리 + 실측 기반 병목/해결책 정리

---

## 1. 로딩에 영향을 주는 것들

### 1-1. 앱 시작(Cold Start) 단계

네이티브 라이브러리 로딩 → JS 엔진 초기화 → 브릿지가 index.js 로드 → 루트 컴포넌트 마운트/API 호출 → 첫 렌더, 4단계로 쪼개짐.

- 가장 큰 병목은 **JS 번들 크기**. 메인 번들은 JS 소스 기준 **4MB 이하** 유지 권장 (Hermes 컴파일해도 그 이상은 파싱 시간 다시 늘어남).

### 1-2. 스레드 블로킹 (JS / UI / Bridge)

- 성능 이슈는 결국 JS 스레드, UI 스레드, 브릿지 중 하나가 막혀서 생김. 원인 파악 없는 최적화는 추측일 뿐.
- New Architecture(Fabric + TurboModules + JSI) 기본 전제 → JSI가 JSON 직렬화 병목 제거 (네이티브 호출당 **200ms → 2ms** 수준으로 개선).

### 1-3. 리스트 렌더링

- FlatList는 뷰포트 밖 아이템을 파괴·재생성 → 부담 큼.
- FlashList는 컴포넌트 재활용(recycle) 방식 → 체감 성능 기여도 가장 큼.

### 1-4. 이미지 로딩/캐싱

- RN 기본 `Image`는 캐싱 기능 거의 없음.
- `expo-image` 전환 시 메모리+디스크 캐싱, placeholder(blurhash/thumbhash), prefetch API 활용 가능.

### 1-5. 네트워크 요청 타이밍

- 시작 시점엔 필수 데이터만. 분석·알림·추천 등 부가 호출은 첫 UI 렌더 이후로 지연.

### 1-6. 작업 우선순위 표

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | New Architecture / Hermes 활성화 확인 | 이후 최적화 효과의 기반 |
| 2 | 번들 크기 감사 (무거운 라이브러리 점검) | 콜드스타트 파싱 시간 직결 |
| 3 | 화면 단위 지연 로딩 (코드 스플리팅) | 화면 10개 이상 앱은 시작 JS 로드량 20~40% 감소 사례 |
| 4 | 리스트 FlashList 전환 (피드/핀 리스트부터) | 체감 성능 개선 폭 가장 큼 |
| 5 | expo-image 전환 + cachePolicy/placeholder | 이미지 많은 화면 스크롤 체감 개선 |
| 6 | 불필요한 리렌더 제거 (memo 등) | 측정 후 원인 컴포넌트부터 |
| 7 | 스플래시를 "준비 상태 기반"으로 숨기기 | 콘텐츠 준비 전 스플래시 사라짐 방지 |

- **작업 방식 팁**: 프로토타입 단계엔 1~3번(기반)만 확실히, 4~5번은 실제로 리스트/이미지가 많아지는 시점(피드·지도 화면 붙는 시점)에 적용. "측정 안 된 걸 최적화하지 말라"가 공통 원칙.

## 2. 로딩 속도 외 UX 고도화 작업

### 2-1. 체감 속도 개선 (Perceived Performance)

- **스켈레톤 스크린**: 빈 화면+스피너 대신 콘텐츠 구조를 미리 보여줘 대기 체감 감소. 핀플 적용 후보 — 피드 카드, 핀 리스트, 프로필 그리드.
- **낙관적 업데이트(Optimistic UI)**: 좋아요·스크랩·팔로우처럼 잦은 액션에서 서버 응답 기다리지 않고 UI 먼저 반영, 실패 시 롤백. TanStack Query `onMutate`로 구현.

```js
onMutate: async (id) => {
  await queryClient.cancelQueries({ queryKey: ['pin', id] });
  const previous = queryClient.getQueryData(['pin', id]);
  queryClient.setQueryData(['pin', id], (old) => ({ ...old, isLiked: true }));
  return { previous };
},
onError: (_err, id, context) => {
  if (context?.previous) queryClient.setQueryData(['pin', id], context.previous);
}
```

- **페이지네이션/무한스크롤**: 커서 기반으로 데이터를 끊어 불러오기 (`useFeed.ts`에 이미 계획됨).

### 2-2. 마이크로 인터랙션 & 햅틱

- 버튼 프레스 시 스프링 애니메이션(reanimated) + `expo-haptics` 진동 피드백 → 액션 확정감 강화.
- 모션은 300ms 이내로 짧고 목적이 분명해야 함, 브랜드 톤과 일관성 유지.
- 잘못된 입력엔 shake 애니메이션 등 즉각적 시각 피드백.

### 2-3. 오프라인/네트워크 대응

- 오프라인 시에도 캐시된 마지막 화면을 보여주고 재연결 시 자동 갱신 (TanStack Query 캐시가 상당 부분 담당).
- 지도/피드처럼 네트워크 의존 큰 화면엔 명확한 재시도 버튼과 에러 상태 UI 필요.

### 2-4. 빈 화면/에러 상태/접근성

- "결과 없음", "네트워크 오류", "권한 없음" 상태를 각각 다르게 디자인 → 체감 품질에 크게 기여 (`shared/components/common/EmptyState.tsx` 계획됨).
- 터치 타겟 최소 44pt, 다크모드 대응, 스크린리더 accessibility label.

### 2-5. 모니터링

- 실사용자 기기 기준 성능/에러 추적 도구(Sentry 등) 도입 → "느리다"는 감을 데이터로 확인.

### 2-6. 우선순위 제안 (핀플 규모 기준)

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | 페이지네이션/무한스크롤 (계획됨) | 데이터량 기본기 |
| 2 | 스켈레톤 스크린 (피드/핀리스트) | 적은 공수 대비 체감 효과 큼 |
| 3 | 좋아요/팔로우/스크랩 낙관적 업데이트 | 소셜 앱 핵심 액션 반응성 |
| 4 | 빈 화면/에러 상태 디자인 | 이미 컴포넌트 계획돼 있어 붙이기만 하면 됨 |
| 5 | 버튼 마이크로 인터랙션 + 햅틱 | 완성도 향상, 후순위 가능 |
| 6 | 오프라인 캐시 전략 | 일정 여유 있을 때 |

## 3. 실제 현업 측정 사례 & 해결책

### 3-1. 실측 사례 — 핏니스 앱 로딩시간 50% 단축

`react-native-bundle-visualizer`로 프로파일링해서 병목 4가지로 좁힌 사례:

- JS 번들 **3.5MB** — 첫 화면에 불필요한 라이브러리·컴포넌트 포함
- 모든 화면 즉시 로드 — 네비게이션 스택이 안 가본 화면까지 처음부터 import
- 고화질 배너 이미지 — 캐싱 없이 로드
- 무거운 상태관리 라이브러리

→ 이 4개만 고쳐서 **로딩시간 50% 감소** 달성. 핵심은 "추측 대신 프로파일러로 확인 후 가장 큰 병목부터 처리".

### 3-2. 실제로 자주 걸리는 병목 Top 5

| 순위 | 병목 | 실측 근거 | 해결책 |
| --- | --- | --- | --- |
| 1 | 리스트 스크롤 | 중급 안드로이드 기기에서 row가 무거우면(이미지+여러 컴포넌트) FlashList가 튜닝된 FlatList보다 일관되게 FPS 이득. 단순 텍스트 리스트는 차이 작음 | 이미 문제 있으면 FlashList로 교체 후 실측, 매끄러우면 유지 |
| 2 | 브릿지/JSI 직렬화 | 구 아키텍처 네이티브 호출당 약 200ms → JSI 전환 시 약 2ms (약 100배 차이) | New Architecture 활성화를 다른 미세 최적화보다 먼저 |
| 3 | 콘솔 로그 | 번들된 앱에서 `console.*` 호출이 JS 스레드 병목 유발 (redux-logger 등 포함) | `babel-plugin-transform-remove-console`로 프로덕션 빌드 자동 제거 |
| 4 | 이미지 | 캐싱 없는 배너·피드 이미지가 체감 로딩 크게 증가 | expo-image(or fast-image) + WebP 압축 포맷 |
| 5 | 불필요한 리렌더 | 컴포넌트가 5번 렌더되면 JS 스레드 작업량도 5배 | `memo`/`useCallback`/`useMemo`, 단 측정된 컴포넌트만 |

### 3-3. 실제로 쓰는 진단 도구

| 도구 | 용도 |
| --- | --- |
| Flipper | CPU/GPU/메모리 프로파일링, 네트워크 인스펙션 |
| Hermes Sampling Profiler | JS 스레드 블로킹 지점 flame graph 확인 |
| react-native-bundle-visualizer | 번들 용량 시각화 |
| React DevTools Profiler | 컴포넌트 리렌더 원인 분석 |
| Sentry Performance / Firebase Performance | 프로덕션 실사용자 기준 시작시간·화면전환·크래시율 |
| Android Studio Memory Profiler / Xcode Instruments | 메모리 누수 확인 |

### 3-4. 실무 원칙

1. 프로파일링이 먼저, 최적화는 그다음 — 추측성 최적화는 시간 낭비이거나 역효과.
2. 가장 큰 병목부터 — 사용자가 가장 많이 보는 화면(홈, 메인 피드) 우선.
3. 릴리즈마다 기준선(baseline) 기록 — 시작시간, 메인 피드 FPS, 5분 사용 후 메모리 등을 추적해 회귀 조기 발견.
4. 작은 팀/런칭 전 단계에선 과최적화 경계 — DAU 100 미만 단계에서 성능 최적화에 과도한 시간 투입은 실수로 꼽힘. "만들고 → 배포하고 → 실제 병목 프로파일 → 최적화" 순서.

## 4. 핀플 적용 관점 메모

- 지도(WebView), 피드(이미지+리스트), 핀등록(이미지 업로드) 세 화면이 실측 시 병목이 가장 먼저 나올 가능성이 높은 지점.
- 실제 기기 테스트 단계에 들어가면 위 진단 도구들로 먼저 프로파일링 후 우선순위 정하는 것을 권장.
